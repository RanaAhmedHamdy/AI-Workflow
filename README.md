# AI-Workflow

Mobile-specific guardrails and workflows that help coding agents make safer changes in native Android and iOS repositories—whether you are starting a new app or changing an existing one.

**Native Android + iOS · New apps + existing apps · Repository-capable coding agents · Lightweight Safety profile available**

AI-Workflow installs repository-owned Markdown instructions and specialist procedures. It guides engineering judgement; it does not certify a release, replace owners, or make an agent autonomous.

## Why mobile needs this

A generic coding agent can correctly “change a model and screen” yet miss the mobile boundary around it:

- an Android process/lifecycle transition or coroutine owner;
- a Room/SQLite migration that damages existing data;
- a Swift concurrency task that outlives its UI owner or scene;
- privacy, permission, capability, or protected configuration work; and
- accessibility, RTL, adaptive-layout, or device-runtime proof that source review cannot establish.

## A 60-second example

Request: **“Add a persisted profile field and show it after refresh/relaunch.”**

| Generic interpretation | AI-Workflow interpretation |
| --- | --- |
| Change model + UI | Persistence/migration → concurrency/lifecycle → runtime evidence |

```text
Task classification: brownfield / android / safety
Detected concerns: concurrency, lifecycle, persistence, schema_migration
Recommended tier: COMPLEX
Required checks:
- android-persistence-migration-readiness: because detected persistence, schema_migration
- kotlin-coroutines-readiness: because detected concurrency
- protected-lifecycle-transaction-review: because detected lifecycle
- android-runtime-evidence-readiness: because detected lifecycle
```

That output is generated by the checked-in route command and demonstrated in the [Android fixture](examples/android-profile-refresh/README.md). The comparable [iOS fixture](examples/ios-profile-refresh/README.md) handles persisted profile state, `MainActor` ownership, async refresh, and scene re-entry.

## Choose how much workflow you want

| Profile | Best for | Process |
| --- | --- | --- |
| `skills` | Specialist mobile knowledge | Minimal |
| `safety` | Most developers | Light — **recommended** |
| `feature` | Proportional feature delivery | SMALL/STANDARD/COMPLEX |
| `full` | Deep governance | Architecture, ADR, design, readiness, acceptance/release controls |

Safety gives a team fact routing, protected-boundary checks, evidence guidance, and a bounded first-change path without requiring a complete feature lifecycle. [Profiles and tiers](docs/PROFILES_AND_TIERS.md) explains the boundary.

## Five-minute quickstart

From a checked-out candidate and a disposable sibling directory, preview then install the Android Safety path:

```bash
cd /path/to/AI-Workflow-release-candidate
mkdir ../ai-workflow-trial
uvx --from . ai-workflow brownfield --platform android --profile safety --target ../ai-workflow-trial --dry-run
uvx --from . ai-workflow brownfield --platform android --profile safety --target ../ai-workflow-trial
uvx --from . ai-workflow route --workflow brownfield --platform android --profile safety --fact persistence --fact schema_migration --fact concurrency --fact lifecycle
```

The candidate is intentionally not advertised as a published remote CLI yet; this local command is the tested route. The complete five-minute trial, exact platform paths, first agent prompt, preview, status, update, and uninstall steps are in [Quickstart](docs/QUICKSTART.md).

## New or existing app?

- **New app (Greenfield):** start from approved product/architecture authority, then use the level of workflow you selected.
- **Existing app (Brownfield):** inspect source, characterize unknown behavior where needed, define a bounded change, then route the relevant mobile checks. You do not have to document the whole application before a narrow safe change.

## Android, iOS, or both

```bash
uvx --from . ai-workflow greenfield --platform android --profile feature --target /path/to/new-android-app
uvx --from . ai-workflow brownfield --platform ios --profile safety --target /path/to/existing-ios-app
uvx --from . ai-workflow brownfield --platform both --profile safety --target /path/to/mobile-repository
```

Dual-platform installs retain separate `.agents/skills/android/` and `.agents/skills/ios/` paths. The intentionally mirrored procedures stay self-contained; they are not flattened simply to reduce a count.

## How routing works

`task facts → concern routes → specialist procedures → escalation/evidence`

You state observable facts such as `persistence`, `concurrency`, `lifecycle`, `privacy`, or `accessibility`; [`ai-workflow route`](docs/QUICKSTART.md) produces deterministic required checks, reasons, and a minimum tier. It does not pretend to understand natural language or authorize a change for you. The checked-in registry has 13 concern routes and about 71 canonical specialist procedures, so routing is the intended discovery path—not a catalogue a developer has to read first.

## Real native demos

The maintained fixtures are deliberately small and local:

- [Android profile refresh](examples/android-profile-refresh/README.md): SQLite migration fallback, ViewModel coroutine ownership, lifecycle-aware Flow collection. Android unit tests and debug build have run locally; emulator relaunch remains unclaimed.
- [iOS profile refresh](examples/ios-profile-refresh/README.md): persisted profile recovery, `MainActor` state, cancellable refresh work, scene re-entry. Xcode simulator build and XCTest have run locally; manual scene/relaunch behavior remains unclaimed.

See [examples](examples/README.md) for scenarios, unsafe-but-non-executable counterexamples, exact facts, route results, and limitations.

## What gets installed and how safety works

The installer adds only package-owned instructions, templates chosen by profile, a route registry, and `.ai-workflow/manifest.json`. It records hashes, refuses unmanaged collisions, preserves modified managed files during update/uninstall, rejects traversal/symlink hazards, and uses staged rollback. Read [Installer lifecycle](docs/INSTALLER_LIFECYCLE.md) and the [profile matrix](docs/PROFILE_CONTENT_MATRIX.md) for detail.

SMALL is genuinely compact: Feature/Full use one `SMALL_FEATURE_RECORD.md`. Durable data, meaningful lifecycle/concurrency work, protected boundaries, or uncertainty promote proportionally; schema migration is COMPLEX.

## Who should use this?

It is a strong fit for developers using coding agents heavily, native Android/iOS teams, legacy repositories, and work where lifecycle/data/configuration mistakes are costly or evidence/approval boundaries matter.

You may not need the full system for throwaway prototypes, autocomplete-only use, teams unwilling to maintain repository instructions, or a simple UI experiment where even Safety feels heavier than the risk.

## Advanced full governance

The Full profile preserves the original deep model: Architecture Spine, ADR lifecycle, Design Authority/Lock, independent reviews, readiness, acceptance, and separate release controls. Start with Safety or Feature unless the change and team need that depth. Greenfield and Brownfield stay distinct because their sources of truth are different.

For the detailed source material, see the [Greenfield package](Greenfield_AI_Mobile_Governance_Package_v1_10_0/README.md) and [Brownfield package](Brownfield_AI_Playbook_Reusable_Package_v4_4/README.md).

## Compatibility, validation, and release posture

The format is architecturally portable because it is repository-owned Markdown rather than a proprietary prompt API. Codex instruction consumption has been manually reviewed; Claude Code and Copilot coding-agent interoperability are not yet verified. See [public claims](docs/PUBLIC_CLAIMS.md).

CI validates repository/routing/installer/package checks and includes separate native demo jobs. The local Android fixture ran unit tests + debug build; the iOS fixture ran Xcode simulator build + XCTest. This remains a pre-v1 release candidate evaluation, not a production-safety or v1 claim.
